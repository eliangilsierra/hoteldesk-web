# Architecture

## Overview

HotelDesk is currently a **client-only single-page application**. There is no backend service, no database, and no network layer — all data lives in memory (generated by Faker) and is persisted to the browser's `localStorage` via Zustand's `persist` middleware.

This is a deliberate starting point, not an oversight: the goal was to validate the UI and workflows for hotel front-desk operations before committing to a backend design. See [`decisions.md`](decisions.md) for the reasoning.

## Layers

```
┌─────────────────────────────────────────────┐
│  Pages (src/pages)                           │  route-level screens
├─────────────────────────────────────────────┤
│  Components (src/components)                 │  layout shell + shadcn/ui primitives
├─────────────────────────────────────────────┤
│  State (src/lib/stores)                      │  Zustand stores: auth-store, data-store
├─────────────────────────────────────────────┤
│  Domain (src/lib/types.ts, lib/utils)        │  types, currency/date formatting
├─────────────────────────────────────────────┤
│  Mock data (src/lib/mock/faker-data.ts)      │  generates rooms/guests/reservations/users
└─────────────────────────────────────────────┘
```

- **Pages** own layout and composition for a route; they read from stores via hooks and render presentational components.
- **Stores** (`useAuthStore`, `useDataStore`) are the single source of truth for application state and own all mutation logic (add/update/delete). Components never mutate state directly.
- **Domain types** (`lib/types.ts`) are shared across stores, mock data, and pages — the contract that keeps them in sync.
- **Mock data** is isolated in `lib/mock/faker-data.ts`. It is the only module that depends on `@faker-js/faker`.

## The mock-to-real-API boundary

The intended seam for introducing a real backend is the `initialize` and CRUD methods inside `src/lib/stores/data-store.ts`. Today:

```ts
initialize: () => {
  const rooms = generateRooms(50);
  set({ rooms, ... });
}
```

Becomes, once an API exists:

```ts
initialize: async () => {
  const rooms = await api.getRooms();
  set({ rooms, ... });
}
```

Because pages only ever interact with the store's public interface (state + actions), swapping the implementation behind `initialize`/`addRoom`/`updateRoom`/etc. should not require changes to any page or component. This is the project's Dependency Inversion boundary today: the "high-level" UI depends on the store's interface, not on how the store gets its data.

We have **not** introduced a separate `services/`/`api/` layer or repository abstraction yet, even though that is the conventional next step once a backend exists. Adding it now, with no real API to integrate against, would be speculative — see the YAGNI note in [`decisions.md`](decisions.md).

## Routing

Route definitions live in `src/routes.tsx` as a flat table of `{ path, element }`, consumed by `App.tsx`. Navigation labels/icons live separately in `src/components/layout/AppSidebar.tsx`, since the sidebar needs presentation metadata (icons, grouping) that the route table doesn't.

## State management choice

Zustand was already in place; it fits this app well: state is UI-local (no server cache to normalize yet), and Zustand's minimal API avoids the boilerplate of Redux for what is currently a small, flat state shape (rooms, guests, reservations, current user).

`@tanstack/react-query` is installed and wired into a `QueryClientProvider` in `App.tsx`, anticipating server-state management once a real API exists — it is not yet used for any query, since there is nothing to fetch.
